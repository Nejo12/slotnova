# 0001 — Managed Hosting and PostgreSQL Provider (R1)

Status: **PROPOSED — awaiting Founder approval**

Evidence reviewed: **2026-09-15**. Issue: [#48](https://github.com/Nejo12/slotnova/issues/48). Baseline: `ef56cbcc7e8a25d1493400baef1d5fc2fe67be35` (`origin/main`, merged PR #47; issue #46 closed). Branch: `feat/pr-17-deployment-env-security`.

## Context and proposed decision

Recommend **Amazon RDS for PostgreSQL 18, Multi-AZ DB instance deployment, with separate API and worker ECS services on on-demand Fargate**. Use one AWS region, provisionally **Europe (Frankfurt), `eu-central-1`**, private database access, direct PostgreSQL connections and certificate-verified TLS. Host the Vite build in private S3 behind CloudFront. Frankfurt is a proposed operational default, not a founder-imposed residency requirement.

This favors database correctness, recovery and explicit security boundaries over the lowest subscription price. Render is substantially easier to operate and cheaper at small sizes; Neon is attractive for disposable branches. Neither advantage removes the connection, security or operational qualifications below. No provider resource was provisioned, no hosted database was tested, and this record does not authorize spending or declare production readiness.

This is only PR-17 Stage A. T072–T075 and T079 remain unchecked. Founder R1 approval is required before Stage B; no implementation PR is opened by this spike.

## Current Slotnova requirements

The governing sources are the constitution, [Phase 1 specification](../../specs/001-platform-foundation-shell/spec.md), [plan](../../specs/001-platform-foundation-shell/plan.md), [tasks](../../specs/001-platform-foundation-shell/tasks.md), [research R1](../../specs/001-platform-foundation-shell/research.md), [data model](../../specs/001-platform-foundation-shell/data-model.md), [ADR-004](../adr/004-backend-data-stack.md), [ADR-008](../adr/008-tenant-isolation.md), [ADR-020](../adr/020-deployment-environments-migrations.md), [R3](0003-job-scheduler.md), [R4](0004-validation-contract-integration.md), and the [security baseline](../security/security-and-audit.md). The accepted Phase 0 gate is unchanged.

- Node 24.20.0, NestJS/Fastify, Drizzle and `pg`; Vite SPA; independently deployable long-running worker. Containers preserve these choices without provider SDKs in domain code.
- PostgreSQL 18 is the preferred baseline, not an unconditional rejection of an otherwise compatible supported major. Current migrations need `citext`; accepted Booking architecture needs `btree_gist`, `tstzrange` and GiST exclusion constraints. JSONB, UUID generation, transactions and `SKIP LOCKED` are native capabilities. No new `pg_cron`, broker, auth service or provider queue is needed.
- Tenant tables retain ENABLE + FORCE RLS. `withWorkspaceContext` checks out one client, begins a transaction, calls `set_config(..., true)`, and commits/rolls back before release. User self-lookup and invitation-capability policies remain narrowly scoped; provider JWT claims do not replace Slotnova authorization.
- PR-16 reserves a session for an advisory lock identifying a unique worker run. A disconnected owner's records become reclaimable only after PostgreSQL releases that lock. There is no timed lease takeover. [Worker README](../../apps/worker/README.md) is authoritative over the earlier R3 pre-implementation discussion.
- `pg-boss@12.31.1` owns `pgboss`, separate from `public.outbox_records`. Library upgrades are a gated release action; normal worker startup uses `migrate=false`. Delayed, recurring and retryable jobs survive process restarts.
- Local, preview/CI, staging and production need isolated data/secrets; migrations run separately from application startup. Ordinary CI must not require real external providers.

Range/exclusion, FORCE RLS and advisory locking are PostgreSQL features, not paid provider add-ons. [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) explicitly distinguishes ordinary roles, owners, superusers and BYPASSRLS; FORCE does not constrain a superuser/BYPASSRLS role. [PostgreSQL locking](https://www.postgresql.org/docs/18/explicit-locking.html) defines session-lock release when a session ends, including ungraceful disconnect. None of the five documented direct models forces transaction pooling. None has received a provider-level PASS in this spike.

## Connection, tenant isolation and worker findings

The proposed API pool, worker pool, pg-boss pool and migration client all connect **directly to the RDS writer endpoint on 5432**. Keep normal `pg.Pool` reuse within each process; it does not multiplex a checked-out client across database sessions. Do not insert RDS Proxy, PgBouncer transaction mode, SQL-over-HTTP or a serverless function lifecycle into the worker path.

A correctly configured transaction pool can preserve the API's transaction-local context, provided BEGIN, settings and every tenant query stay on one backend until COMMIT/ROLLBACK. That does **not** make it safe for PR-16: session ownership must survive those transaction boundaries. Any future API-only pooling change requires isolation-suite evidence and distinct connection configuration.

Disconnection detection is not instantaneous. Network partitions, database maintenance/failover, proxy behavior and server TCP/idle settings can delay lock release or terminate a healthy owner. Connection lifetime and idle-session policies must be checked in staging. Process-kill tests below prove application recovery on local PostgreSQL, not a cloud failover RTO. Continue at-least-once semantics; future external effects still need durable idempotency.

TLS is a material distinction: Slotnova's `DATABASE_SSL=require` creates `{ rejectUnauthorized: true }`; libpq's `sslmode=require` generally promises encryption without hostname verification. Those settings are not interchangeable. Render documents its internal limitation explicitly; selecting `no-verify` would be a deliberate security tradeoff, not a harmless connection-string fix. RDS's published CA bundle can be trusted by Node, for example through `NODE_EXTRA_CA_CERTS`, while preserving hostname verification. Test API, migration CLI and pg-boss separately; prevent URL SSL options from unexpectedly overriding driver settings. No TLS configuration was changed here.

Neon PrivateLink can preserve the ordinary hostname using private DNS. Render also offers outbound AWS private links on Pro+, but does not support private DNS on those links; its documented SNI override requirement and Neon endpoint registration need a joint compatibility test before recommending that combination. It is **not** correct to say Render cannot use PrivateLink. [Render private-link limitations](https://render.com/docs/private-link).

Supabase's public direct endpoint defaults to IPv6; its IPv4 add-on is distinct from the shared session pool. Its private endpoint must be verified separately. Disable/unexpose the unused Data API and prevent grants to `anon`/`authenticated` on Slotnova tables: several foundation tables intentionally are not tenant-owned. Keep Slotnova sessions, authorization and policies; do not adopt `service_role` or `auth.uid()` as substitutes. [Data API controls](https://supabase.com/docs/guides/api/securing-your-api).

## Database roles and pg-boss provisioning

Required model, to be provisioned only after approval:

| Principal | Required scope | Must not receive |
| --- | --- | --- |
| Bootstrap administrator | Create database, ordinary roles, memberships and required extension grants; emergency access separately controlled. RDS master/admin stays outside app tasks. | Routine API/worker use. |
| Business migration login | Own Slotnova foundation/business objects and migration ledger; run reviewed SQL via `DATABASE_MIGRATION_URL`; required database/schema CREATE for trusted extensions. Ordinary non-superuser is sufficient for current migrations. | Exposure to app/worker runtime. |
| `slotnova_app` | Non-superuser, NOBYPASSRLS; existing explicit table grants and RLS policies. `DATABASE_URL` uses an environment-specific app credential. | Business ownership, schema CREATE, migration/scheduler ownership, audit UPDATE/DELETE/TRUNCATE. |
| Scheduler owner | Own only `pgboss` and its objects. Prefer NOLOGIN; the gated scheduler provisioning principal can SET ROLE to it. | Business-schema ownership or BYPASSRLS. |
| Worker login | Own credential through `WORKER_DATABASE_URL`; inherit scheduler-owner rights within `pgboss`; explicit outbox maintenance/session cleanup/workspace enumeration grants; membership permitting `SET LOCAL ROLE slotnova_app` for invitation sweeps. | Business DDL, migration-role membership, superuser/BYPASSRLS. |

RDS supports customer role administration through its [restricted administrative role](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.Roles.rds_superuser.html). Render permits SQL-created users; Neon console/API-created roles have elevated membership, so use SQL-created app/worker roles; Supabase's default administrative and service roles are not app credentials. Railway's template administrator similarly must not be reused for tenant traffic. Validate role attributes **and memberships/ownership**, not only role names, on any provider.

The local role spike uncovered and resolved a misleading assumption: **`migrate=false` does not mean pg-boss needs only DML privileges**. Version 12.31.1 manages queues and partitions during normal operation. A DML-only role failed with SQLSTATE 42501, `permission denied for schema pgboss`; an ordinary worker inheriting ownership of only the scheduler schema succeeded, while ALTER on `public.users` remained forbidden. The production worker uses the same connection credential for its outbox and scheduler pools, so the role must satisfy both bounded responsibilities.

Provision business migrations first, then use the pinned library's supported construction/upgrade API in a separately gated release action under the scheduler owner. The scratch test used exported `getConstructionPlans('pgboss', { createSchema: false })` on a precreated schema; normal `PgBoss.start()` then used `migrate:false`. Do not copy pg-boss internals into Drizzle migrations, create a second outbox, or enable production auto-migration. Scheduler runtime ownership permits DDL within `pgboss`; gating is a release/process boundary, not a claim that runtime cannot alter that schema. Shared owner membership is a conscious privilege cost of the current library/configuration.

The local probe tested queue partition creation, cron registration, enqueue, restart, fetch and completion. The existing worker suite separately exercised actual recurring executions, delayed delivery, retries, concurrent workers, transaction rollback and process restart durability. No provider-specific pg-boss certification is claimed.

## Networking, limits and environment topology

Proposed production topology: separate AWS production account/VPC; public HTTPS ALB for API ingress; API and worker Fargate services in private application subnets; RDS primary and synchronous standby in private DB subnets across two availability zones. Database security groups accept only application/worker and gated release-task groups. No public DB endpoint. Public web assets use CloudFront with a private S3 origin; workers have no public ingress. Fargate desired counts keep processes running; avoid Spot for the initial worker availability baseline.

Serve browser API calls under the same public origin as the SPA: CloudFront routes `/v1/*` to the HTTPS ALB, with API caching disabled, all required methods/cookies/query parameters and security headers forwarded, and `Set-Cookie` preserved. Only static assets receive asset caching; SPA navigation fallback must not rewrite API errors. This preserves host-only cookie visibility without broadening cookie domains. [CloudFront caching policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-cache-policies.html). The ALB origin access and trusted proxy chain need explicit Stage B configuration and verification.

Start with one API and one worker service replica, each provisionally 0.25 vCPU/1 GiB, and a provisionally `db.t4g.small` RDS instance with 20 GiB gp3 storage; these are sizing hypotheses, not load-tested capacity. RDS Multi-AZ here means the **two-instance synchronous standby** model, not a three-instance Multi-AZ cluster or Aurora. [RDS Multi-AZ semantics](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html). One API replica is not application-level HA. T073 must account for rolling-deploy overlap and per-process rate-limit state before claiming global limits or scaling horizontally.

Private tasks still need image pulls, logs, secrets and approved outbound providers. Budget two AZ-local NAT gateways initially; dedicated VPC endpoints can be evaluated against actual traffic and cost later. Database traffic stays private independently of outbound internet access. This does not promise that external Identity/payment/email services are private.

At the current defaults, API pool 10 + worker pool 10 (including its reserved owner client) + pg-boss's separate default `pg.Pool` 10 = **30 potential connections** per one-API/one-worker deployment, before release/admin sessions. A full rolling overlap can reach 60. Provision at least 80 usable client slots or reduce pool sizes with evidence, reserve administration capacity, and monitor saturation. `DATABASE_POOL_MAX` does not currently configure pg-boss's separate pool. RDS's actual `max_connections` depends on class/parameters; inspect it rather than borrowing a generic published maximum. Render's small paid plans advertise 100; Neon depends on compute size; Supabase Small lists 90 direct connections shared with platform services; Railway depends on image/server config. Pooled client limits are not database backend capacity. [Neon compute limits](https://neon.com/docs/reference/compatibility), [Supabase compute](https://supabase.com/pricing).

Staging uses a separate nonproduction account/VPC, DB instance, secret namespace, app/worker roles, scheduler schema and buckets, in the same chosen region. A smaller Single-AZ DB is acceptable for normal staging; temporarily reproduce Multi-AZ topology for failover evidence. CI uses disposable PG 18 containers. Hosted previews, when needed, use disposable synthetic-data databases and credentials isolated from staging and production; expire them explicitly. Do not fork production customer/session data into previews. Local development follows the existing [runbook](../runbooks/local-dev.md) and [quickstart](../../specs/001-platform-foundation-shell/quickstart.md).

Render supports Frankfurt and four other regions, with Pro environment network isolation. Neon offers same-region AWS PrivateLink; Supabase similarly requires matching project/VPC regions. Railway offers regional service placement and environment private networking, but exact template-region availability and TLS trust remain hosted checks. [Render regions](https://render.com/docs/regions), [Render network isolation](https://render.com/docs/private-network), [Railway regions](https://docs.railway.com/deployments/regions), [Railway private network](https://docs.railway.com/networking/private-networking).

## Alternatives not selected

- **Render all-in-one**: best simpler alternative, but internal certificate verification and asynchronous HA durability are real disadvantages for the proposed posture. A Founder-approved different risk posture could reopen it; it is not rejected for missing RLS, worker support or PITR.
- **Neon**: native SQL fit and useful preview economics; continuous worker polling weakens scale-to-zero value, and private connectivity adds a second provider/control plane. Render+Neon PrivateLink requires SNI/endpoint integration evidence; cheap public connectivity is not silently equivalent.
- **Supabase**: compatible database route exists, but private-network tier plus PITR cost and unused Data API/Auth surface are a poor Phase 1 fit. Hosted PG 18 remains unverified, not the sole rejection reason.
- **Railway database template**: newer PITR/HA/upgrade tooling deserves credit. Exact extension/TLS configuration and greater database maintenance responsibility leave it behind fully managed candidates.
- **Aurora instead of RDS, or Kubernetes instead of ECS**: no present capacity/availability requirement justifies the additional service-specific complexity; not separately certified by this spike. Fly/other container hosts remain possible, but add no demonstrated advantage to the private same-provider topology selected here.
